# Architecture & rationale

This document explains *why* this package exists, *how* it works end to end,
and how it compares to the legacy `build-batman_adv` script and to what other
Freifunk communities do. Start with `README.md` for the quick how-to; read this
when you want the full picture.

## 1. The problem

`tecff/scripts/build-batman_adv` builds the out-of-tree `batman-adv` kernel
module by hand for a *specific* kernel and wraps it with `checkinstall`. The
painful properties:

| Behaviour in the old script | Consequence |
|---|---|
| `--requires "${REQUIRED_KERNEL}"` pins the `.deb` to one exact `linux-image-X.Y.Z-…-amd64` | Every kernel-point-release upgrade breaks the dependency / leaves an orphan module; you must rebuild. |
| Branches on `6.1.0*`→bookworm, `6.12.*`→trixie, `5.10.0*`→bullseye + `~deb11u/~deb12u/~deb13u` suffixes | One `.deb` per distro × kernel; the matrix grows. |
| Runs `make` + `checkinstall` **on the gateway** | The gateway itself carries a full build environment (compiler, kernel headers, `checkinstall`, git, …). |
| `check()` polls `modinfo` vermagic/version to detect drift | You must *invoke* it (cron/Ansible) and then react. Drift between detection and rebuild. |
| Patches via `git am /usr/src/batman_adv_patches/*` into a throwaway clone | Not version-controlled, not reproducible, lost on re-clone. |
| Manual `depmod -a` | Easy to forget. |

The goal: **one source package, kernel-version-independent, that rebuilds
itself automatically when the kernel changes, with the heavy toolchain off the
gateway.**

## 2. What DKMS is (mental model)

DKMS (Dynamic Kernel Module Support) is a framework shipped by the Debian
`dkms` package. You give it *source* for a module; it keeps a registry
(`/var/lib/dkms/`) and, whenever a kernel is installed or removed, compiles the
module for that exact kernel and drops the `.ko` into
`/lib/modules/<kernel>/extra/` followed by `depmod`. The trigger is a hook the
`linux-image-*` postinst calls: `dkms autoinstall`. Modules whose `dkms.conf`
sets `AUTOINSTALL="yes"` are rebuilt automatically; others only on demand.

So unlike the old flow (build → wrap → install a kernel-pinned binary), DKMS
ships **sources** and defers compilation to the moment a kernel exists on the
target. The package is therefore `Architecture: all` and tiny (a few hundred
KB of C sources + a config file).

Crucial consequence: **the target host must have a compiler.** DKMS *is* "compile
on the target". There is no mode of DKMS that avoids gcc on the gateway. What
we *do* move off the gateway is the **packaging** toolchain (dpkg-dev,
debhelper, dh-dkms, git, quilt, checkinstall). See §3.

## 3. Host roles

Two distinct machines; only one needs the heavy toolchain.

### Build host (you provide; Debian)
Produces the source `.deb`. Nothing is compiled here — the package is
`Architecture: all`, just sources. Installed once:

```
apt install dpkg-dev debhelper dh-dkms git xz-utils devscripts
```
(`devscripts` only for `dch` when bumping versions.)

Does **not** need: kernel headers, gcc, make, the target kernel.

### Target host (host03.tecff.de; Debian, kept lean)
Receives the `.deb`; DKMS compiles the module here. Irreducible minimum:

```
apt install dkms linux-headers-$(uname -r)
```
`dkms` and `linux-headers-*` pull in `gcc`, `make`, `binutils`, `perl`, `libelf`,
`libssl`, `bc`, `kmod` via their dependencies — i.e. exactly what turning C into
a `.ko` requires and nothing more.

Does **not** need: dpkg-dev, debhelper, dh-dkms, git, quilt, checkinstall,
build-essential (the meta).

Rough footprint: the compiler slice on the target is ~150–250 MB installed; the
full packaging+build stack the old script forced onto the gateway is ~400–600 MB.
More importantly, the target now contains **zero packaging tools** — only what is
physically required to compile a module.

> If even a compiler on host03.tecff.de is unacceptable, DKMS is the wrong tool and you
> should instead prebuild per-kernel `.deb`s on the build host (essentially your
> current script, automated). That trades "lean target" for "rebuild per kernel",
> which is the opposite of the goal here.

## 4. End-to-end pipeline

### Initial install
1. **Build host:** `./build.sh` → `build/batman-adv-dkms_2026.3-1~tecff1_all.deb`.
2. **Ship to target** (§8): `scp` or an apt repo on host03.
3. **Target:** `apt install ./batman-adv-dkms_…_all.deb` (or `apt install
   batman-adv-dkms` from your repo). apt pulls `dkms` + `linux-headers-*` +
   compiler as dependencies.
4. The package's **postinst** (auto-generated by `dh-dkms`) runs
   `dkms add` → `dkms build` → `dkms install` for the running kernel.
   Result: `/lib/modules/<running>/extra/batman-adv.ko` + `depmod`.
5. `modprobe batman-adv` (or your existing `/etc/modules` line from
   `tecff/ansible`'s `batman` role) loads it. Unchanged from today.

### Kernel upgrade (the win)
6. `apt upgrade` installs a new `linux-image-amd64`. Its postinst calls
   `dkms autoinstall`.
7. Because our `dkms.conf` has `AUTOINSTALL="yes"`, DKMS builds `batman-adv`
   for the **new** kernel *before* you reboot.
8. After reboot, the module is already in
   `/lib/modules/<new>/extra/batman-adv.ko` and autoloads. No human in the loop.

### Removal
9. `apt remove batman-adv-dkms` → prerm runs `dkms remove -m batman-adv -v
   2026.3 --all` (auto-generated), cleaning `/usr/src/batman-adv-2026.3/` and
   all built `.ko`s.

## 5. How the Debian package is structured

| File | Role |
|---|---|
| `debian/changelog` | **Single source of truth** for the version. `build.sh` parses the top entry to derive the upstream git tag (`v<upstream-version>`) and the Debian revision. Bumping = one `dch -v` line. |
| `debian/control` | `Source: batman-adv-dkms`; binary `Package: batman-adv-dkms`, `Architecture: all`, `Depends: dkms (>= 3.0), ${misc:Depends}`, `Recommends: linux-headers-amd64 \| linux-headers-generic`. `Build-Depends: debhelper-compat (= 13), dh-dkms`. |
| `debian/rules` | Modern `dh $@ --with dkms` sequencer. Overrides `dh_auto_build` (nothing to compile at build time) and `dh_auto_install` (stages the upstream tree into `debian/batman-adv-dkms/usr/src/batman-adv-<ver>/`). Upstream ships no `dkms.conf`; `dh-dkms` generates the authoritative one from our `.dkms` template. |
| `debian/batman-adv-dkms.dkms` | The `dkms.conf` **template**. `dh-dkms` turns this into the real `dkms.conf` inside `/usr/src/batman-adv-<ver>/` and generates the postinst/prerm/postrm from it. Contains `AUTOINSTALL=yes`, `-j$(nproc)`, `KERNELPATH=${kernel_source_dir}`, `INSTALL_MOD_STRIP=1`, explicit `BUILT_MODULE_NAME`. |
| `debian/source/format` | `3.0 (quilt)` — patches live in `debian/patches/series`. |
| `debian/patches/series` | Empty; ready for quilt patches (replaces `/usr/src/batman_adv_patches/` + `git am`). |
| `debian/copyright` | GPL-2.0+ for upstream and debian/. |
| `build.sh` | Orchestrates: parse changelog → sync `PACKAGE_VERSION` in the `.dkms` → clone upstream at `v<ver>` → reproducible `orig.tar.xz` → overlay `debian/` → `dpkg-buildpackage`. |

`dh-dkms` auto-generates the maintainer scripts that the old MUC reference wrote
by hand (`postinst` calling `/usr/lib/dkms/common.postinst`, `prerm` calling
`dkms remove --all`). Less code, correct across `dkms` versions.

## 6. Old-script pain → DKMS fix

| Pain (§1) | Fix |
|---|---|
| `--requires` exact-kernel pin | `Architecture: all`, no kernel dependency; DKMS rebuilds per kernel. |
| Per-distro `~debXXu` + kernel-family sniffing | Deleted. One source `.deb` serves bullseye/bookworm/trixie and any kernel. |
| Build on the gateway | Build host produces the source `.deb`; target only compiles. |
| `check()` polling | Gone. `AUTOINSTALL=yes` + kernel postinst hook rebuilds proactively. |
| `git am` patches in a throwaway clone | `debian/patches/` (quilt), tracked in git, reproducible. |
| Manual `depmod -a` | DKMS runs `depmod` after install. |

## 7. How this relates to Freifunk references

Researched `freifunkMUC` and `freifunk-darmstadt` (both upstream of `tecff`):

- **`freifunkMUC/batman-adv` (branch `debian`, 2015)** is the proven DKMS
  template — a ~7-file `debian/` wrapping the upstream tree plus a `dkms.conf`
  that MUC authored themselves (upstream does **not** ship one — verified by
  cloning the current `git.open-mesh.org/batman-adv.git` tree: no `dkms.conf`
  present). We model on MUC's skeleton but modernise: debhelper compat 7→13,
  manual `postinst`/`prerm` → auto-generated by `dh-dkms`, `Standards-Version`
  3.8.1→4.7.0, `Rules-Requires-Root: no`, `3.0 (quilt)`, reproducible
  `orig.tar.xz`. Critically, MUC's `dkms.conf` **lacked `AUTOINSTALL`** (so it
  wouldn't auto-rebuild on kernel upgrade) — our template adds it, plus `-j`,
  `KERNELPATH`, explicit `BUILT_MODULE_NAME`.
- **`freifunkMUC` *today*** dropped DKMS and uses the **in-kernel `batman-adv`
  module + stock Debian `batctl`** (visible in `ffmuc-salt-public`). See §10.
- **`freifunk-darmstadt`** distributes via an **aptly** repo at `apt.ffda.io`,
  built with `git-buildpackage` in a Docker image. The packaging recipe itself
  is on a bot-blocked self-hosted git, so only the *distribution infra* was
  recoverable. We borrow the apt-repo distribution idea in §8.
- **`tecff/ansible`** `roles/batman` only does `apt: batctl` + `modprobe` (loads
  the in-kernel module); the newer module `.deb` was always built out-of-band by
  `build-batman_adv`. This package replaces that out-of-band build.

## 8. Getting the `.deb` onto host03.tecff.de

### Option A — one-off scp (simplest, fine for a single server)
```
scp build/batman-adv-dkms_2026.3-1~tecff1_all.deb root@host03.tecff.de:/tmp/
ssh root@host03.tecff.de 'apt install -y /tmp/batman-adv-dkms_2026.3-1~tecff1_all.deb'
```

### Option B — tiny apt repo on host03 (scales; mirrors Darmstadt's aptly idea)
host03 already serves HTTP at `/var/www/html/fw` (firmware). Reuse the web
server for a flat apt repo — no aptly needed for one or two packages:

```
# on host03, once:
install -d /var/www/html/apt/tecff/pool/main/b/batman-adv-dkms
cp batman-adv-dkms_*.deb /var/www/html/apt/tecff/pool/main/b/batman-adv-dkms/
( cd /var/www/html/apt/tecff && dpkg-scanpackages --arch all pool /dev/null | gzip -9 > Packages.gz )

# on host03 (and any other consumer), once:
cat > /etc/apt/sources.list.d/tecff.list <<'EOF'
deb [trusted=yes] http://host03.tecff.de/apt/tecff ./
EOF
apt update && apt install batman-adv-dkms
```
`[trusted=yes]` is acceptable on a trusted LAN initially. For proper hygiene,
sign with `apt-ftparchive release` + a GPG key and drop `trusted=yes`; or adopt
`aptly` (Darmstadt's tool) when the repo grows.

With Option B, future upgrades are just: build host publishes new `.deb` →
`apt update && apt upgrade` on consumers → DKMS rebuilds. Fully hands-off.

## 9. Monitoring build failures

DKMS can fail to build for a new kernel if batman-adv hasn't adapted to a kernel
API change between releases. That surfaces as `dkms status` showing `failed`
instead of `installed` — silent otherwise. Add a cheap check on host03:

```
# /usr/local/sbin/dkms-healthcheck.sh
#!/bin/sh
out=$(dkms status 2>&1)
echo "$out"
echo "$out" | grep -q '\bfailed\b' && exit 1 || exit 0
```
```
# crontab: mail/alert if any module is failed
*/15 * * * * /usr/local/sbin/dkms-healthcheck.sh || systemctl --no-block start your-alert-mailer
```
(Wire `your-alert-mailer` to whatever notification you use; or have it POST to
your monitoring.) The healthy steady state is `batman-adv/2026.3: installed` for
every kernel line.

## 10. Alternative considered: the in-kernel module

**batman-adv is in mainline Linux** — proven from two primary sources:
- Local kernel (here Arch 7.1.4): `modinfo batman-adv` reports `intree: Y`
  (that flag literally means "compiled from in-tree kernel source"), version
  `2025.5`, located at `kernel/net/batman-adv/batman-adv.ko.zst`, with
  `CONFIG_BATMAN_ADV=m`.
- Upstream's own `README.external.rst` (cloned from `git.open-mesh.org`):
  *"The batman-adv module is shipped as part of the Linux kernel and as an
  external module."*

`freifunkMUC` *appears* to use the in-kernel module today (their public
`ffmuc-salt-public` Salt states have no DKMS state and reference only stock
Debian repos) — though private pillars aren't fully visible, so this is
inference, not certainty.

The in-kernel module is strictly simpler — zero maintenance, no DKMS, no
compiler on the gateway. **But it is frozen at whatever version your Debian
kernel shipped.** Upstream's `README.external.rst` states the external module's
purpose explicitly: it *"allows to get new features without upgrading to a newer
kernel version and to get batman-adv specific bug fixes for kernels that are not
supported anymore."* That is precisely your situation: you track upstream
releases (currently `v2026.3`) independently of the Debian kernel cycle.
Upstream declares support for **Linux 5.10 – 7.2**.

So the real trade-off is **currency vs. maintenance burden**: the in-kernel
module costs nothing but lags upstream; the DKMS module tracks upstream but
needs a compiler on the target and occasional rebuild-fix attention (§9). Your
existing `build-batman_adv` script — pinning `v2025.4` and enabling deprecated
DEBUGFS/SYSFS — shows you've already chosen "track upstream". DKMS preserves
that choice while removing the per-kernel-rebuild pain.

If you ever stop needing a newer-than-kernel batman-adv (mesh migrated off
deprecated interfaces, Debian's bundled version suffices), switching to the
in-kernel module deletes this entire package. To enable those deprecated knobs
meanwhile, set them on the `MAKE[0]` line in `debian/batman-adv-dkms.dkms`
(documented there), e.g. `CONFIG_BATMAN_ADV_DEBUG=y`.

> **Verify on the target:** check whether Debian's own kernel already enables
> `CONFIG_BATMAN_ADV`. If it does, the DKMS module (installed to
> `/lib/modules/<k>/extra/`) must override the in-kernel one via `depmod`
> directory priority — `/extra/` wins over `/kernel/`, which is why
> `DEST_MODULE_LOCATION="/extra/"` is set. Confirm with
> `modinfo -k <k> batman-adv` pointing at the `/extra/` path after install.

## 11. Patches & config

- **Quilt patches:** drop into `debian/patches/`, list in `debian/patches/series`.
  Applied on top of the upstream tarball at build time, stripped afterwards
  (standard `3.0 (quilt)`). Supersedes `/usr/src/batman_adv_patches/` + `git am`.
- **Compile-time config flags** (from the current upstream `Makefile`):
  `BATMAN_V=y`, `BLA=y`, `DAT=y`, `DEBUG=n`, `MCAST=y`, `TRACING=n` (defaults
  marked `*` in `README.external.rst`). Override by appending to `MAKE[0]` in
  the `.dkms` file (see the comment block there). NB: the 2015 MUC reference
  listed `NC` (network coding) — that knob no longer exists upstream.

## 12. Side note: `batctl`

`tecff/scripts/build-batctl` builds the userspace tool with `checkinstall` too.
`batctl` is **not** a kernel module — DKMS does not apply. Two sane options:
- use Debian's stock `batctl` package if its version is protocol-compatible with
  your module (batctl and batman-adv should track the same release);
- or package `batctl` as a normal `Architecture: amd64` Debian package on the
  build host (straightforward debhelper, no DKMS). Out of scope for this repo,
  but easy to add as a sibling package later.

## 13. Failure modes to know

- **Kernel API breakage** between batman-adv releases → `dkms status` shows
  `failed` for the new kernel. Fix: bump to a newer upstream tag (`dch -v …` +
  `./build.sh`) and republish. The healthcheck in §9 catches it.
- **Missing headers on target** → DKMS can't build. Mitigated by `Recommends:
  linux-headers-*` and the install instructions.
- **Secure Boot** (if host03 enforces it): unsigned out-of-tree modules won't
  load under Secure Boot. Either disable Secure Boot on host03, or sign the
  module with a MOK (DKMS supports `SIGN_TOOL`/`mok_signing_key` — add to the
  `.dkms` file if needed). Most Freifunk gateways run with Secure Boot off.
- **`dkms.conf` collision**: upstream sometimes ships its own `dkms.conf`;
  `debian/rules` deletes it so the `dh-dkms`-generated one (with `AUTOINSTALL`)
  is authoritative.
